프로브는 UI 를 통해 노드별·축별로 붙입니다. 각 프로브 뒤에는 **어댑터**가 있습니다 —
한 종류의 대상을 어떻게 확인하는지 아는 작은 모듈입니다.

## 내장 어댑터

| 어댑터   | 확인하는 것                              | 자격 증명                  |
| --------- | --------------------------------------- | -------------------------- |
| `tcp`     | 호스트/포트로 TCP 연결                   | 없음                       |
| `http`    | HTTP(S) 요청, 상태 코드/지연             | 없음                       |
| `k8s`     | 클러스터 내부 쿠버네티스 요약            | 클러스터 내 ServiceAccount |
| `proxmox` | Proxmox VE 노드/게스트 상태 (PVE API)    | API 토큰                   |
| `system`  | `node_exporter` 스크레이프 (`:9100/metrics`) | 없음                   |

모든 어댑터는 **부드럽게 degrade 합니다** — 환경이 설정되지 않았으면 오류를 내지 않고
그냥 `unknown` 을 돌려줍니다.

## 설정

### Proxmox VE

먼저 전용 사용자를 만들고, **PVE → Datacenter → Permissions → API Tokens** 에서 그
사용자용 토큰을 발급합니다:

```bash
SORACK_PROXMOX_USER=sorack@pve!tokenid
SORACK_PROXMOX_TOKEN=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
SORACK_PROXMOX_INSECURE=true   # PVE 가 자체 서명 인증서를 쓸 때만
```

:::danger[`root@pam` 의 토큰은 쓰지 말고, **Privilege Separation** 은 켜 두십시오]
sorack 은 읽기만 합니다. 사용자에게 `/` 에 대한 `PVEAuditor` 만 주고 그 외에는 아무
권한도 주지 마십시오.

**자기 ACL 항목이 없는** 토큰이라고 해서 무해한 것이 아닙니다. 권한 분리가 켜져
있으면(`privsep=1`, 기본값) 아무 권한도 없지만, 꺼져 있으면 그 사용자가 가진 모든
것을 물려받습니다. `root@pam` 이라면 그건 클러스터 전체입니다. 두 경우는 바깥에서
보면 완전히 똑같습니다 — 어느 쪽이든 ACL 행이 없습니다. 어느 쪽인지는 토큰을 발급할
때 눌린 체크박스 하나에 달려 있습니다.

그래서 아무 일도 못 하는 것처럼 보이는 `root@pam` 토큰이, 실제로는 쿠버네티스 Secret
안에 앉아 무언가 쓰기를 기다리는 클러스터 전체 자격 증명일 수 있습니다. 읽기 전용
모니터링이 그런 것을 들고 있을 이유는 없습니다.

인스턴스마다 토큰을 따로 주십시오. 개발과 운영 인스턴스가 하나를 공유하면, 더 약한
쪽이 뚫리는 순간 양쪽이 함께 넘어갑니다.
:::

### node_exporter (system 프로브)

자격 증명이 없습니다. 호스트에
[node_exporter](https://github.com/prometheus/node_exporter)를 설치하면(systemd
몇 줄이면 됩니다) system 프로브가 `:9100/metrics` 를 스크레이프합니다.

### 쿠버네티스

클러스터 내부 ServiceAccount 를 씁니다 — 설정할 환경변수가 없습니다. RBAC 은
`deploy/base/rbac.yaml` 에 있습니다(읽기 전용: 시크릿이 아닌 리소스에 대한
`get`/`list`).

프로브 설정이 무엇을 지목하는지에 따라 세 가지 형태가 됩니다:

```jsonc
{ "type": "k8s", "namespace": "alpha" }                         // 네임스페이스
{ "type": "k8s", "namespace": "alpha", "service": "gateway" }    // Service 하나
{ "type": "k8s", "namespace": "alpha", "cronjob": "db-backup" }  // CronJob 하나
```

`namespace` 만 있거나 — 아무것도 없으면 노드의 이름을 씁니다 — 네임스페이스를
보고합니다: pod/deployment/statefulset 준비 상태, service 와 ingress 개수, 상한이
걸린 워크로드 목록. 아무것도 찾지 못하면 `ok` 가 아니라 `unknown` 을 보고합니다. 빈
네임스페이스와 건강한 네임스페이스는 서로 다른 답이고, "프로브가 그 종류를 읽을 수
없었다" 는 세 번째 답입니다.

`service` 는 노드에 `svc_type`, `clusterIP`, `ports`, `selector`, `endpoints` 를
채우고, 그 뒤에 무언가 있는지로 점수를 냅니다 — 준비된 엔드포인트가 없는 Service 는
이름은 해석되지만 아무것도 응답하지 않습니다.

한 가지 예외가 있고, 오퍼레이터를 돌리는 클러스터라면 어디서든 중요합니다: **다른
무언가가 만든 Service 는 그것만 보고 판정하지 않습니다.** Service 에
`ownerReferences` 가 있으면, 엔드포인트가 비어 있어도 장애로 보지 않고 `unknown` 을
보고하면서 소유자의 이름을 알려 줍니다.

"여기 뒤에 뭔가 있어야 하는가?" 는 Service 가 답할 수 있는 질문이 아닙니다. 인스턴스를
요청한 것이 소유자이므로 답은 소유자에게 있고, 그곳은 **이 프로브가 들여다볼 수 없는
곳**입니다. 인스턴스가 하나인 데이터베이스에는 읽기 복제본이 없으므로 그 읽기 전용
Service 에 엔드포인트가 없는 것이 맞습니다. 관측은 옳고, 그것을 장애로 채점하는 것이
틀립니다. 0 으로 스케일된 Deployment 를 준비된 것으로 세는 규칙과 같습니다 — **0 이라는
의도는 실패가 아닙니다.**

`cronjob` 은 `schedule`, `suspend`, `lastScheduleTime`, `lastSuccessfulTime`,
`lastStatus` 를 채우고, **가장 최근 실행의 결과만으로** 점수를 냅니다. 실패한 실행은
사실입니다. 늦었다는 것은 사실이 아닙니다. CronJob 이 늦었다고 말하려면 그 스케줄에
대한 임계값이 필요하고, 추측한 임계값은 주간 작업에 대해 없는 경보를 만들어 내면서
시간 단위 작업은 놓칩니다. 타임스탬프는 사람이 판단할 수 있도록 보고하되, 프로브는
판정하지 않습니다.

### 발견

요청하지 않으면 꺼져 있습니다. 네임스페이스 프로브에 `discover: true` 를 넣으면
찾아낸 Service 와 CronJob 마다 노드를 만듭니다:

```jsonc
{ "type": "k8s", "namespace": "apps", "discover": true }
```

**프로브가 스스로 판정할 수 있는 종류만** 노드가 됩니다. Deployment 에는 프로브 형태가
없으므로, 아무도 아무 말도 해 줄 수 없는 노드가 되는 대신 네임스페이스의 집계에
남습니다.

소유자가 있는 Service 도 같은 이유로 빠집니다 — 건강 여부가 프로브가 읽을 수 없는
곳에서 결정되는 노드이기 때문입니다. 이들은 네임스페이스 보고 안에 **무엇이
만들었는지로 묶여** 계속 보이며, 그 묶음이 이들에 대해 의미를 갖는 유일한 묶음입니다.
데이터베이스 역할마다 Service 를 하나씩 만드는 클러스터에서는 이게 대다수입니다.
실측한 클러스터에서는 발견 가능한 Service 40개가 28개가 되었고, 떨어져 나간 열두 개는
정확히 오퍼레이터가 소유한 것들이었습니다.

발견된 노드는 **이미 프로브가 붙은 상태로** 도착합니다 — 발견은 좌표를 알고 있고, 그
좌표가 바로 Service 또는 CronJob 프로브가 받는 값입니다.

발견된 id 는 클러스터 좌표입니다 — `apps/cronjob/nightly-backup` — 그래서 두 번째
사이클은 같은 노드를 찾을 뿐 새로 만들지 않습니다. 이미 가지고 있던 노드가 그 객체를
프로브로 가리키고 있으면 발견은 그것을 건드리지 않습니다: **노드는 프로브로 객체를
소유한다고 선언합니다.** 내가 붙인 이름과 클러스터의 이름은 일상적으로 다르고, 이름으로
맞추면 이름을 붙일 만큼 신경 쓴 바로 그 노드들이 중복됩니다.

‼ **발견은 절대 삭제하지 않습니다.** 객체가 사라지면 `meta.discovered.goneAt` 을
설정하고 노드는 사용자가 지우도록 남겨 둡니다. RBAC 에 거부된 프로브나, 컨디션이 나쁜
API 서버를 가리킨 프로브는 비워진 네임스페이스를 본 프로브와 똑같은 것을 봅니다 —
그게 노드를 지울 수 있다면 하루 잘못된 오후가 지도를 지우고 성공을 보고할 것입니다.
다시 나타난 노드는 자기 표시를 스스로 지우고, 어떤 종류를 읽지 못한 사이클은 그 종류를
아예 표시하지 않습니다.

쿠버네티스는 이력 한도를 넘은 완료된 Job 을 삭제합니다 — 기본값으로 성공 3개와 실패
1개 — 그래서 실행 사이의 대부분 구간에는 물어볼 Job 이 남아 있지 않습니다. CronJob
자신의 status 가 그 공백을 덮습니다: `lastSuccessfulTime` 이 `lastScheduleTime` 과
같거나 그 이후라면 가장 최근에 예약된 실행이 끝났다는 뜻이고, Job 없이도 `ok` 로
읽힙니다.

`unknown` 으로 남는 것은 **마지막 성공 이후에 시작됐고 그 Job 이 사라진** 실행입니다.
실패, 아직 실행 중, 정리되어 사라짐은 서로 다른데 그것을 가를 수 있는 것이 아무것도
남아 있지 않습니다. 메시지는 하나를 골라 말하는 대신 그렇다고 말합니다.

## 어댑터 만들기

소스를 추가하는 일은 의도적으로 작습니다: `api/src/health/adapters/` 아래 **파일
하나**와 **등록 호출 하나**. 어댑터는 노드의 프로브 설정을 받아 상태와 선택적 메트릭을
돌려주는 프로브 함수를 export 하고, 등록하면 그 프로브 타입이 UI 에서 선택 가능해집니다.

:::tip
어댑터는 설정되지 않았을 때 `unknown` 을 돌려주므로, 새 어댑터를 배포한 뒤 노드 단위로
천천히 적용해도 아직 참여하지 않은 것이 깨지지 않습니다.
:::
